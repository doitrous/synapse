# Connect Cortex — 5,000 concurrent-student Vite-preview frontend delivery report

**Test date:** 24 August 2026  
**Instrumented run:** 5,000 simultaneous fresh student sessions  
**Result:** Vite-preview frontend availability passed; frontend delivery thresholds failed

This is a local Vite-preview frontend delivery test. It is **not** evidence of
production API, authentication, MariaDB, Supabase, storage, CDN, or infrastructure
capacity.

## Scope and traffic model

The test exercised the production frontend build through one local Vite preview
process on `127.0.0.1`. Each virtual student opened one route and downloaded the
complete static module graph needed by a fresh browser session. The traffic mix
was:

| Journey | Students | Requests per session |
| --- | ---: | ---: |
| Dashboard | 1,750 | 44 |
| Question Bank | 1,500 | 59 |
| Library | 1,000 | 49 |
| Practical | 750 | 55 |

Each session modelled up to six browser connections. All 5,000 sessions began
together, producing a peak of 30,000 outstanding asset requests.

This test did **not** use student credentials, write production data, call the
authenticated APIs, exercise MariaDB, exercise Supabase Auth, test media storage,
or touch production infrastructure. It measures local Vite-preview frontend
delivery under a fresh-session spike, not the complete deployed architecture.

## Traffic and availability

| Metric | Result |
| --- | ---: |
| Total requests | 255,750 |
| Successful responses | 255,750 (100%) |
| Failed requests | 0 |
| Test duration | 71.75 seconds |
| Sustained request rate | 3,564.3 requests/second |
| Data transferred | 1,762.95 MiB |
| Sustained throughput | 206.1 Mbit/second |

The process did not crash, reject a request, or return a non-200 response.

## Latency

| Metric | p50 | p95 | p99 | Maximum |
| --- | ---: | ---: | ---: | ---: |
| Individual request | 8.27 s | 10.10 s | 11.93 s | 12.77 s |
| Complete fresh session | 70.06 s | 71.63 s | 71.63 s | 71.64 s |

The configured targets were at most 2 seconds for p95 request latency and at
most 15 seconds for a p95 fresh-session load. Both targets failed.

### Journey completion time

| Journey | p95 fresh-session load |
| --- | ---: |
| Dashboard | 61.44 s |
| Question Bank | 71.63 s |
| Library | 70.33 s |
| Practical | 70.66 s |

The Question Bank has the largest request graph and was the slowest journey.

## Server process telemetry

The server process was sampled every 500 ms. The monitor collected 177 samples
over 88.12 seconds, including a short idle period before and after the 71.75-second
load window. CPU percentages use 100% as one fully occupied logical core.

| Resource | Baseline | Average | p95 | Peak |
| --- | ---: | ---: | ---: | ---: |
| CPU | — | 234.3% | 518.0% | 561.1% |
| Resident memory | 108.2 MiB | 1,519.1 MiB | 2,036.3 MiB | 2,060.6 MiB |
| Host 1-minute load | — | 4.6 | 6.5 | 6.5 |

Resident memory grew by 1,952.5 MiB from baseline to peak. A post-test sample
showed approximately 1,460 MiB still resident after traffic had stopped. That
retention must be checked under the actual production server; Vite preview is a
validation server and is not itself the intended production asset origin.

## Assessment

- **Reliability:** Pass. The server completed the spike with no errors.
- **Vite-preview frontend delivery:** It sustained about 3,564 requests/second and 206 Mbit/second.
- **User experience:** Fail. Queueing pushed p95 fresh-session load to 71.63 seconds.
- **CPU pressure:** High. The process reached the equivalent of 5.6 logical cores.
- **Memory pressure:** High. Resident memory peaked just above 2 GiB and remained
  elevated after the test.
- **Primary bottleneck:** Static asset delivery capacity and request fan-out in
  local Vite preview, not an observed application error condition.

## Recommended next actions

1. Serve immutable `/assets` through an HTTP/2 or HTTP/3 CDN and repeat the same
   traffic model against staging. Meeting the 15-second target for this exact
   cold-start transfer would require roughly 1 Gbit/second of aggregate delivery,
   which a distributed edge is designed to absorb.
2. Reduce the 44–59-request fresh-session graphs by reviewing very small shared
   chunks and preloading only the common critical path.
3. Repeat the test against the actual production server image rather than Vite
   preview, with a process memory limit and garbage-collection telemetry enabled.
4. Run a separate staging-only authenticated test for `/api/session`, `/api/me`,
   shared catalogue reads, and per-user state reads/writes. Capture MariaDB query
   latency, pool wait time, active connections, lock time, and slow queries.
5. Add event-loop delay, open-socket count, response compression ratio, and CDN
   cache-hit rate to the next report so server compute and network queueing can be
   separated directly.
