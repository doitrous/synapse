## Non-negotiable rules
1. **The book is the source.** A definition, article section, explanation or answer must come from the cached page text and cite its page (`source_citation` / `original_wording` / citation `locator_page`). If the book does not say it, leave the field blank with a `field_notes` reason. Never fill from model knowledge.
2. **File ownership.** Write only the files named in your lane. Never edit a file whose header contains `Generated by scripts/kasr/build-batches.ts` — create a hand-authored file beside it instead. Never touch `101-ISK-*` files unless your lane says so.
3. **No duplicates.** Before minting a concept run `node "Instruction Manual for Content Creation/tools/find-existing.mjs" "<shortest distinctive word>"` and grep `^## id` / `^## label` / `^## canonical_key` / `^## title` across `docs/Kasr-Source-Imports/concept/*.md` and `article/*.md`. If the idea exists live or in any batch, reference its id (or write an update row) — do not mint again.
4. **IDs.** Concepts: `mintConceptId` from `scripts/kasr/seeds/types.ts` (hash of `kau:<module>:<canonical_key>`), e.g.
   `node --experimental-strip-types -e 'import {mintConceptId} from "./scripts/kasr/seeds/types.ts"; console.log(mintConceptId("103 BMS","msk","lower-limb.thigh.femoral-triangle"))'`
   (read `types.ts:429-450` for the real signature first). Articles: `ART-<SUBJ>-<SLUG>`; questions hand-authored: `QST-<SUBJ>-<SLUG>-<NNN>`; claims `CLM-<SYS>-<SLUG>-<NN>`; citations `CIT-<SLUG>-<NN>`; spans `SPN-<SUBJ>-<SLUG>-<NN>`. Resources are manifest `src_…` ids only.
5. **Copy the shape of an existing sibling record** in the same folder (same `## field` set, same order) — the importer silently drops unknown keys. Concept records need 50 of 52 fields used; empty list columns are `[clear]`; a blank block is "untouched", not empty. Never put `[clear]` in a text/prose column — verify with `node --experimental-strip-types scripts/kasr/check-column-parsers.ts <file>`.
6. **`subject`** is one of the 20 catalogue ids (`src/data/curriculumCatalog.ts`): cvs resp renal gi neuro endo msk pharm fnd dev haem imm inf obs gyn androl psy derm mul pop. **`module_subject`** is `"<module> > <Department> > <Chapter> > <Sub-heading>"` using the academic tree's exact wording.
7. **Concepts, articles and questions are one set.** Every new concept must be covered by an article you write (`related_concepts` on the article, `article_ids` on the concept); every question's `main_concept` must be covered by an article in `library_ids`.
8. **Validate before you finish** (all from repo root):
   - `npm run medical:batch -- <file> --with <every sibling concept/article file of your module>` for each of your files → `errors: []`. Since 57ef0d4 this also enforces the catalogue: `universities` non-empty and valid (`kau`), `module_subject`'s first segment must be a module the record declares in `modules`, `subject` must be one of the 20 catalogue ids (`renal` not `ren`, `neuro` not `neu`).
   - `node --experimental-strip-types scripts/kasr/check-concept-ids.ts <your concept files>` → clean for your files.
   - `npm run medical:presence` (note only lines naming your ids).
   - `grep -n '"\[clear\]"\|^\[clear\]$' <file>` and `check-column-parsers.ts` → no sentinel in a text column.
   - `npm run medical:simulate -- <all your module's concept/article/evidence/question/written files> --emit /tmp/sim-<lane-slug>.json` then `npm run medical:audit -- --source /tmp/sim-<lane-slug>.json` → `errors: []` for your ids; `created`/`updated` as intended.
9. **Never** run `git commit`, `git push`, `build-batches.ts`, `--sweep`, a bare `build-coverage.ts`, or any import. The orchestrator commits.
9b. **Textbook fallback (ruling 2026-08-23).** A banked question whose concept the department book never teaches does NOT leave that concept unteachable: add a SHORT teaching section (a paragraph to a page) to the nearest existing article — or a small article if none fits — sourced from the question book's own explanation plus a standard textbook citation; `field_notes`: "not in the department book; taught here because the question book asks it"; two-sided link; an evidence claim with the textbook citation; scope limited to what the questions ask, nothing beyond. The question stays in the bank.
9c. **[clear] while teaching.** An article's `related_concepts` may sit at `[clear]` although the article already teaches the concepts (six 101 articles did) — the two-sided pass adds the back-links; never assume `[clear]` means "nothing to link".
10. **Brick wall → consult, don't guess.** If you are blocked — a gate you cannot get green, a format you cannot determine, a source file whose text is missing or unreadable, an ambiguity only the faculty or the orchestrator can settle — do NOT skip it silently, invent around it, or widen your file ownership. Finish everything that does not depend on it, then END YOUR TURN with a section headed `BLOCKED` stating exactly what you need (file, page, id, decision). The orchestrator will answer and resume you with the answer.
11. **Missing source material.** If the manifest/page cache lacks a paper, a page range, or a sitting you need: (a) check the Telegram study-group library at `/Users/doitrous/Desktop/Uni Telegram Data - Organized` and `scripts/telegram-library/discovery.json` for the file; (b) if it is not there, list it under `BLOCKED` as a Telegram fetch request (module, exam type, year, what the file should contain). Never fabricate the missing content.
12. **"Live" is a 10-day-old snapshot.** `medical:simulate` and `find-existing.mjs` treat `server/data/medical-library-v1.json` (regenerated 2026-08-12) as live state; anything imported since is invisible. Consequences: an update-shaped row for an id that is NOT live is silently created as a stub; a FULL record on a live id replaces every named field (can evict a university or un-publish). So: write sparse update rows only (id + changed fields); keep a list of every id you assumed live and put it in your report; simulate one directory/kind at a time when two files could touch the same id.
13. **Report** (as your final message AND to your scratchpad report path): files written, record counts per file, per-chapter coverage table (chapter → concepts → articles), validation command outputs (summarised, errors verbatim), and an explicit list of what the book did not support so was left out.
